# Reflection

I drew the boundaries around observable effects. `search_catalog` answers a lookup request without creating a database or changing a file. `save_book` performs one persistent change for one known book and one named list. `build_reading_list` owns the higher-level goal of preparing a saved list for a topic. It calls the same search and save implementations used by the standalone tools, rather than duplicating their logic. That distinction keeps the Data and Action tools useful independently while making the workflow visible and testable. I treated no search matches as a normal Data result, but as an explicit `NO_MATCHES` workflow error because a saved reading list cannot be produced. Duplicate saves return `already_saved`; this makes retries predictable and prevents duplicate entries.

Three tools fit this deliberately small use case: inspect information, save an individual item, or request the complete workflow. A larger library assistant would need additional capabilities, such as viewing or removing saved entries, but adding them here would violate the assignment’s tool count. The bundled catalog makes demonstrations reproducible, although its shelf labels are illustrative and it does not represent live campus holdings. A next step would be replacing it with a library API while preserving the tool contracts. Another would be adding authenticated user ownership and an atomic batch persistence layer. Currently, each save commits separately, so a later failure reports completed IDs and supports safe retry instead of claiming that the whole workflow was rolled back.
